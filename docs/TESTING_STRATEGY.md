# ShopFlow Testing Strategy

## Current baseline

The application is built with Next.js, TypeScript, Supabase SSR, PostgreSQL, and Zod. The root package scripts currently expose development, production build, start, and ESLint commands. A dedicated test script and committed automated test suite were not identified during this repository review.

This document is a proposed test plan. It does not claim that the cases below are already implemented or passing.

## Test layers

### 1. Unit tests

Prioritize deterministic business logic that does not require a live Supabase project.

| Area | Cases |
|---|---|
| Phone normalization | Pakistani local, country-code, spaced, punctuated, and unsupported inputs |
| Zod validation | Valid and invalid login, customer, supplier, product, and sale payloads |
| Role permissions | Each role's allowed and denied permissions; unknown permission and invalid role behavior |
| Money and totals | Discounts, quantities, rounding, zero values, and boundary conditions in pure helpers |

### 2. Integration tests

Use an isolated test Supabase project or a disposable local database. Never run destructive tests against production.

- Authenticated user can access only their own shop context.
- A user from shop A cannot read or mutate shop B records.
- Cashier, manager, shop owner, and super-admin permissions are enforced server-side.
- Sale creation and cancellation preserve stock, IMEI, payment, and audit invariants.
- Failed multi-step operations do not leave partial financial or inventory updates.

### 3. Database security tests

For every tenant-owned table:

- Verify Row Level Security is enabled.
- Verify SELECT, INSERT, UPDATE, and DELETE policies use the authenticated user's shop membership.
- Test both authorized and cross-tenant access.
- Check service-role usage remains server-only.
- Review RPC functions and storage policies for equivalent tenant boundaries.

### 4. End-to-end tests

After unit and integration foundations are in place, cover critical user journeys:

1. Sign in and sign out.
2. Create a product and receive stock.
3. Complete a cash sale.
4. Complete a credit sale and record a customer payment.
5. Sell an IMEI-tracked handset and verify the IMEI state.
6. Confirm a cashier cannot access owner-only settings.
7. Confirm shop A cannot access shop B data.

## Suggested implementation order

1. Add a test runner and TypeScript-compatible test configuration.
2. Add unit tests for `normalizePhone` and `hasPermission`.
3. Add table-driven tests for the Zod schemas in `src/lib/validations.ts`.
4. Add integration tests for RLS and shop isolation using a dedicated test database.
5. Add browser-level tests for POS and inventory flows.
6. Run tests in GitHub Actions and publish coverage only after coverage is generated by the test runner.

## Safe test data and secrets

- Use synthetic users, shops, products, customers, and IMEI values.
- Keep test credentials in CI secrets or local ignored environment files.
- Never copy production customer data into test fixtures.
- Do not expose Supabase service-role credentials to browser code.
- Do not run destructive test setup or cleanup against production.

## Definition of done

A test is complete only when it is committed, deterministic, independently runnable, and included in CI. A green build alone is not evidence that business rules or tenant isolation are tested.
